GitHub 入門 · 第 11 篇 · Actions 與 Pages(進階選讀)

寫一個 YAML,讓 GitHub 自動幫你測試與發佈網站

從最小的 workflow 開始:push 之後自動 checkout 與跑指令,在 Actions 分頁看日誌,再用 GitHub Pages 把靜態網頁變成公開網站。

TL;DR workflow 是 .github/workflows/ 裡的 YAML:事件(on)→ job → step,第一步通常是 actions/checkout。結果看 Actions 分頁;金鑰放 secrets;網站用 Settings → Pages 從分支或 Actions 發佈。

把重複的事交給機器

用「自動化工廠的流水線」來想

每次 push 之後,你都想跑一次測試、檢查格式、打包、發佈。這些事每次都一樣,GitHub Actions 就是讓 GitHub 在特定事件(push、開 PR、打 tag)發生時,依你寫的腳本自動幫你做,結果會顯示在 PR 的 Checks 上(第 7 篇看到的綠勾、紅叉就是它)。

GitHub Pages 則是把 repo 裡的靜態網頁(HTML、CSS、JS)變成一個公開網站,可以直接從分支發佈,也可以用 Actions 建置後發佈。

七個名詞

名詞
白話說明
workflow
一份自動化流程,寫在 .github/workflows/ 底下的 .yml 檔。
event(on)
觸發條件,例如 push、pull_request。
job
一組在同一台機器上依序執行的步驟。多個 job 預設同時進行。
runner
跑 job 的機器。ubuntu-latest 是 GitHub 提供的 Linux 虛擬機。
step
job 裡的一個動作:跑一個指令(run)或使用別人寫好的 action(uses)。
action
可重複使用的步驟,例如 actions/checkout 把 repo 下載到 runner。
GitHub Pages
把 repo 的靜態檔案發佈成網站的服務。

全貌:事件觸發,runner 依序做事

一個 workflow 的生命週期:事件 → 一台乾淨的機器依序跑步驟 → 結果顯示在 GitHub 上。

  1. 1事件:你 push、開 PR,或其他設定的時機。
  2. 2步驟:機器是全新的,所以第一步一定是 checkout,把你的程式碼拿下來。
  3. 3結果:成功是綠勾、失敗是紅叉;也可以接著部署到 Pages。

照著做:七個步驟

1

建立第一個 workflow 檔

workflow 就是 repo 裡的一個檔案,放在固定位置 GitHub 才找得到。

mkdir -p .github/workflows
  1. 用編輯器新增檔案 .github/workflows/ci.yml。
  2. 貼上下面的內容。YAML 對縮排很敏感:用空白,不要用 Tab,每層縮排 2 個空白。
.github/workflows/ci.yml
name: CI
on:
  push:
    branches: [ {branch} ]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: 取得程式碼
        uses: actions/checkout@v4
      - name: 顯示檔案
        run: ls -la
      - name: 跑測試
        run: echo "在這裡放你的測試指令,例如 npm test"
  1. name:這個 workflow 在 Actions 頁顯示的名字。
  2. on:什麼時候跑。這裡是 push 到 {branch},以及任何 PR。
  3. jobs → test → runs-on:有一個叫 test 的 job,跑在 Ubuntu 上。
  4. steps:依序做的事。uses 是用別人寫好的 action;run 是執行指令。
小技巧actions/checkout@v4 的 @v4 是 action 的版本。官方文件的範例可能使用更新的主版本,新增時以當時文件為準。
2

commit 並 push,觸發第一次執行

workflow 一進到預設分支(或對應的分支),下一次符合事件就會跑。

git add .github/workflows/ci.yml
git commit -m "新增 CI workflow"
git push
你會看到push 成功後,不需要任何手動動作。GitHub 會自動開始執行。
3

在 Actions 分頁看結果

每次執行都有完整的日誌。失敗了,就是從這裡找原因。

  1. 到 repo 頁面,點上方的 Actions 分頁。
  2. 左側列出 workflow 名稱(CI),點進去,再點最新的一次執行。
  3. 左側 Jobs 底下點 test,可以展開每一步的日誌。
你會看到執行中是黃色圓點,成功是綠色勾勾,失敗是紅色叉叉。每個 step 可以展開看輸出。
注意紅叉時,點進失敗的那一步看紅色錯誤訊息。九成是縮排錯誤、指令打錯,或測試真的沒過。
4

讓 PR 也會自動檢查

上面的 on 已經包含 pull_request,所以每個 PR 都會自動跑。

  1. 開一個 PR(見第 6 篇)。
  2. PR 頁面下方的合併區塊會出現 Checks:顯示 CI 是通過或失敗。
  3. 搭配第 7 篇的規則集,可以設定「CI 通過才能合併」。
你會看到合併區塊列出 CI / test,通過時是綠勾。
5

用 secrets 保存金鑰

測試或部署需要金鑰時,放在 Actions secrets,不要寫進 workflow 檔(見第 10 篇)。

  1. repo 的 Settings → 側邊欄 Secrets and variables → Actions。
  2. Secrets 分頁按 New repository secret,填名稱與值,按 Add secret。
  3. 在 workflow 的 step 裡用環境變數傳入。
      - name: 使用 secret
        env:
          API_KEY: ${{ secrets.API_KEY }}
        run: ./deploy.sh
你會看到日誌裡 secret 的值會被遮成 ***。
注意來自 fork 的 PR 預設拿不到 secrets,這是為了安全,不是壞掉。
6

啟用 GitHub Pages(從分支發佈)

最簡單的發佈方式:把網頁檔案放在某個分支,讓 Pages 直接發佈。

  1. 確認 repo 根目錄(或 /docs 資料夾)有 index.html,並已 push。
  2. repo 的 Settings → 側邊欄 Code, planning, and automation 區塊的 Pages。
  3. Build and deployment → Source 選 Deploy from a branch。
  4. Branch 選 {branch},資料夾選 / (root) 或 /docs,按 Save。
你會看到稍等一兩分鐘,Pages 設定頁上方會出現 Your site is live at … 與網址。專案網站網址通常是 https://{me}.github.io/{repo}/。
注意Pages 能不能用在私人 repo,依你的方案而定;公開 repo 一般可以直接使用。找不到選項時,以官方文件與你帳號實際的畫面為準。
7

(進階)用 Actions 建置後發佈 Pages

網站需要先建置(例如用工具把 Markdown 轉成 HTML)時,改成讓 Actions 建置並部署。

  1. Pages 設定頁 Source 選 GitHub Actions。
  2. GitHub 會建議幾種現成的 workflow 範本,選一個符合你工具的,或用現有的 workflow。
  3. 之後每次 push,Actions 會建置並更新網站。
你會看到Actions 分頁出現部署的執行紀錄;完成後網站內容更新。
小技巧純 HTML 的靜態網站,不需要建置,步驟 6 就夠了。

常見卡關

workflow 沒有跑

依序檢查:

  1. 檔案位置是不是 .github/workflows/xxx.yml(資料夾名稱與副檔名都要對)。
  2. on 的事件和分支是否符合你的操作(例如設定 push 到 main,你卻 push 到別的分支)。
  3. YAML 縮排有沒有錯。到 Actions 分頁,常常會直接顯示語法錯誤。
Actions 日誌說 Permission denied 或需要權限

預設的 token 權限有限。需要寫入(例如推送、開 Release)時,在 workflow 加上 permissions: 區塊,只給需要的最小權限。

permissions:
  contents: read
Pages 顯示 404

檢查三件事:index.html 是否在你選的分支與資料夾的最外層;檔名是否完全是小寫的 index.html;是否等了一兩分鐘讓部署完成。也可以在 Actions 分頁看有沒有 Pages 的部署紀錄。

網站樣式或圖片壞掉,但 HTML 有出來

專案網站的網址帶有 repo 名稱(/{repo}/),所以資源路徑要用相對路徑(style.css),而不是以 / 開頭的絕對路徑(/style.css)。

要付費嗎?

公開 repo 使用 GitHub 提供的標準 runner 一般是免費的;私人 repo 的免費額度依方案而定(個人免費方案每月有一定額度的使用量,Linux 計費最便宜,Windows 與 macOS 較貴)。額度與價格會調整,請以 GitHub 帳號的 Billing 頁與官方文件為準。
