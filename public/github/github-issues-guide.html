好的 Issue 讓對方不用追問

Issue 是專案的問題單,Projects 是把它們排成看得見進度的看板。同一張 Issue 分兩個視角講:「提出問題的人(提出者)」和「負責處理的人(維護者)」。

TL;DR 提出者:先搜尋、標題說清楚、附上重現步驟。維護者:貼標籤、指派、排進看板,用 PR 說明裡的 Closes #編號 在合併時自動關閉。

Issue 是專案的「問題單」

用「客服工單」來想

有人發現 bug、想要新功能、或有疑問,就開一張 Issue(工單)。維護者收到後分類、決定要不要做、指派給誰;做完之後用 Pull Request 把它關掉。討論、決策與進度都留在同一個地方,不會散落在聊天室裡。

Issue 的品質決定對方要不要追問你。好的 Issue 讓對方不用追問。

七個名詞

名詞
白話說明
Issue / #編號
一張問題單。每張有自己的編號,例如 #12,可以在別處用 #12 引用它。
label(標籤)
分類用的貼紙,例如 bug、enhancement、good first issue。
assignee(指派)
這張單由誰負責。
milestone(里程碑)
把一批 Issue 歸到同一個目標,例如「v1.0」,並顯示完成進度。
Projects(專案看板)
把 Issue 與 PR 排成看板或表格,用欄位(如 Status)追蹤進度。
Closes #12
寫在 PR 說明裡的關鍵字。這個 PR 合併進預設分支時,會自動關閉 Issue #12。
Close reason
關閉有不同理由:已完成、不打算做(not planned)、重複(duplicate)。

全貌:一張 Issue 從提出到關閉

提出者主要做第 1 步,維護者主要做第 2、3 步;但任何人都可以在討論中留言幫忙。

  1. 1提出:寫標題與內文,送出 Issue。提出者
  2. 2分類與指派:貼標籤、指派、排進里程碑與看板。維護者
  3. 3解決並關閉:PR 說明寫 Closes #編號,合併後自動關閉。維護者

選一個視角,照著步驟做

同一張 Issue,兩個人各做各的事。可以隨時切換視角對照著看。

你已經會的用瀏覽器操作 GitHub、貼文字與圖片
這次要新學的搜尋重複、寫清楚的標題與重現步驟、保持追蹤
1

先搜尋,確認不是重複的

多數專案已經有人回報過。先搜尋可以幫你省時間,也不會讓維護者重複處理。

  1. 進入專案頁面,點上方的 Issues 分頁。
  2. 在搜尋框輸入關鍵字(錯誤訊息的關鍵字最有效)。預設只搜尋 Open 的 Issue,記得也看看 Closed。
  3. 找到類似的,就在那張 Issue 底下留言補充你的情況,不要再開新的。
你會看到搜尋結果列出符合的 Issue,每張有編號、標題、標籤與留言數。
2

按 New issue,選對範本

如果專案設了範本,會讓你先選類型(回報問題、功能建議……)。範本會把該寫的欄位預先列好。

  1. 在 Issues 頁按綠色的 New issue。
  2. 若出現範本清單,選最符合的一個,按 Get started。
你會看到跳到填寫頁面,可能已經預填了一些標題與段落。
注意找不到 Issues 分頁?代表這個 repo 沒有開啟 Issue 功能(維護者可以在 repo 的 Settings 裡開關)。這時請看專案 README 有沒有說明聯絡方式。
3

寫一個一眼看懂的標題

維護者每天會看到很多張 Issue,標題是他決定要不要點進來的依據。

不好的標題
好的標題
壞了
設定頁按「儲存」後變成空白(Chrome 126,macOS)
請修好!!!
匯出 CSV 時中文變成亂碼
有個想法
建議:搜尋框支援依標籤篩選
小技巧標題就是結論:說出「什麼東西、在什麼情況下、怎麼了」。
4

內文:讓對方能重現問題

維護者不在你的電腦前。能照著做就看到同樣問題,這張 Issue 就成功了一半。

內文範例(回報 bug)
## 發生什麼事
按下「儲存」之後頁面變成空白。

## 重現步驟
1. 打開 設定 頁
2. 修改暱稱
3. 按下「儲存」

## 預期結果
顯示「已儲存」。

## 實際結果
頁面空白,沒有任何訊息。

## 環境
- 瀏覽器:Chrome 126
- 作業系統:macOS 14
你會看到重現步驟、預期結果與實際結果分開寫,維護者只需要看一眼就能判斷。
隱私貼錯誤訊息或日誌時,先檢查有沒有密碼、token、個人資料再貼。Issue 預設是公開的。
5

附上截圖與日誌

一張圖勝過一百字,但也要挑重點。

  1. 截圖可以直接貼上或拖曳到內文框,GitHub 會自動上傳並產生圖片語法。
  2. 較長的日誌用程式碼區塊包起來(前後各一行三個反引號 ```),或用 <details> 收合,避免整頁被洗版。
你會看到預覽分頁裡圖片已顯示,日誌是等寬字型的灰底區塊。
6

送出之後:追蹤與回覆

按 Submit new issue 就完成了。接下來的重點是保持聯繫。

  1. 你會收到 email 通知。維護者問問題時,盡快回覆。
  2. 被貼上 needs more info 之類的標籤,就是在等你補資料。
  3. 被關閉也看一下原因:completed 表示已解決;not planned 或 duplicate 是正常的決定,不是針對你。
你會看到Issue 頁面上方狀態是 Open(綠色);解決後變成 Closed(紫色)。
你已經會的建立 repo、git push
這次要新學的標籤、指派、Projects 看板、範本,以及 Closes #編號
1

收到通知,先判斷這張單的類型

有人開 Issue 時你會收到通知,Issues 分頁的數字也會增加。先讀標題與內文,判斷是 bug、功能建議、提問還是重複。

你會看到Issue 頁右側有 Assignees、Labels、Projects、Milestone 幾個區塊,後面幾步都是在這裡操作。
2

貼標籤

標籤讓你(和志工)之後能篩選。不需要很多,一組簡單的就夠。

  1. 點右側 Labels 旁的齒輪,勾選合適的標籤。
  2. 常見組合:bug、enhancement、question、documentation、good first issue(適合新手上手)。
  3. 缺資料就貼上 needs more info 之類的標籤,並留言說明需要什麼。
你會看到標籤出現在 Issue 標題下方與列表上,可以點標籤篩選同類的 Issue。
3

指派負責人與里程碑

沒有人負責的 Issue,通常就不會被做。

  1. Assignees 旁點齒輪,選負責的人(也可以選自己)。
  2. 有版本規劃時,在 Milestone 選擇對應的里程碑,例如 v1.0。
你會看到右側顯示負責人頭像;里程碑頁面能看到「已關閉 / 總數」的進度條。
4

放進 Projects 看板

Projects 把散落的 Issue 與 PR 排成一個看得見進度的表格或看板。

  1. 在 repo 或你的帳號 / 組織頁面進入 Projects,建立一個新的 Project,選 Board(看板)版型。
  2. 預設有 Todo、In Progress、Done 三欄,對應內建的 Status 欄位。
  3. 回到 Issue,右側 Projects 旁選擇這個 Project;也可以在看板上直接把 Issue 加進來,再拖曳卡片換欄位。
你會看到卡片出現在看板的 Todo 欄,拖到 In Progress 後,Issue 的 Status 也跟著更新。
小技巧Projects 的介面更新得比較頻繁,實際畫面請以 GitHub 為準。
5

範本讓每個人一開始就填對欄位,你就不用一直追問。範本是放在 repo 裡的檔案。

about: 回報 bug 或使用上的問題

---

## 實際結果

- 瀏覽器 / 版本:
- 作業系統:
  1. 在 repo 建立資料夾 .github/ISSUE_TEMPLATE/,把上面的內容存成裡面的 bug-report.md。
  2. commit 並 push 到預設分支(通常是 main)。
你會看到之後別人按 New issue,就會先看到「回報問題」這個選項,標題與標籤已預填。
6

用 Pull Request 解決並自動關閉

解決問題的 PR,在說明裡寫關鍵字加編號,合併時就會自動關閉對應的 Issue。

寫在 PR 說明裡
Closes #12
# 也可以用 Fixes #12 或 Resolves #12
你會看到PR 頁面右側 Development 會顯示連結的 Issue。合併後,Issue 自動變成 Closed。
注意自動關閉只有在 PR 合併進預設分支時才會發生。合併到其他分支,Issue 不會被關。
7

關閉:選對理由

不是每張 Issue 都要做。清楚地關閉,對提出者也是一種尊重。

  1. Issue 頁底部的 Close issue 旁有下拉選單,選 Close as completed(已完成)、Close as not planned(不打算做),或在重複時選 Close as duplicate。
  2. 關閉前先留言說明原因並感謝對方。
你會看到Issue 狀態變成紫色或灰色的 Closed,並標示關閉理由。

同一張 Issue,兩邊在同一個時間點各做什麼

點選下面的階段,看提出者與維護者分別該做什麼。

提出者

    維護者

      常見卡關

      PR 合併了,Issue 卻沒有自動關閉

      依序檢查:

      1. 關鍵字是不是寫在 PR 說明(或 commit 訊息)裡,而且格式是 Closes #編號。
      2. PR 是不是合併進預設分支(通常是 main)。
      3. 編號對不對、是不是同一個 repo。
      一張 Issue 裡塞了好幾件事

      拆成多張。每張只處理一件事,才能各自指派、各自關閉,也才好用 Closes #編號 對應 PR。在原本那張留言附上新 Issue 的編號即可。

      我的 Issue 被標成 duplicate 關掉了

      這不是拒絕你。代表已經有同一個問題的 Issue 在處理,討論集中在那一張比較有效率。到那張補上你的情況,並按右側的訂閱追蹤進度。

      Issues 分頁不見了

      代表這個 repo 沒有啟用 Issue。維護者可以在 repo 的 Settings 頁的功能區塊開啟 Issues。
