GitHub 入門 · Pull Request

把修改交給別人:Pull Request 從零開始

給只會 git add、git commit、git push、git clone 的你。同一件事分兩個視角講:「送出修改的人(發起者)」和「收到修改的人(repo 擁有者)」。每一步都說明為什麼要做、要打什麼、會看到什麼。

TL;DR PR 是一張「請把我這個分支的修改合併進你的專案」的申請單。發起者要新學的只有 fork、分支、remote、在網頁上開 PR;擁有者全程在網頁上看 Files changed → Review → Merge,不需要任何新指令。

PR 是什麼?為什麼不直接 push?

用一本共用筆記本來想

別人的專案就像「別人的筆記本」。你沒有權限直接在上面寫字(git push 會被拒絕)。所以流程是:① 影印一份(fork)→ ② 在影印本上修改(commit、push)→ ③ 附上一張紙條請對方看(Pull Request)→ ④ 對方決定要不要貼進原本的筆記本(merge)。

所以:PR 不是 git 指令,而是 GitHub 網站的功能。git 負責把你的修改送上 GitHub;「請對方看、討論、同意」這整段是網站在處理。

全貌:一個 PR 的旅程只有五個動作

先看地圖,後面每一步都會回到這張圖。左邊兩個方塊在 GitHub 網站上,右邊是你的電腦。

  1. 1Fork:在網頁上複製一份到你的帳號。發起者
  2. 2Clone:把「你的 fork」抓到電腦。發起者
  3. 3Push:改完 commit 後,推到你的 fork 的新分支。發起者
  4. 4開 PR:在網頁上請原作者看並合併;之後擁有者審查、按 Merge。發起者擁有者
  5. 5同步:合併後,把原作者最新的 main 拉回你的電腦與 fork。發起者

選一個視角,照著步驟做

同一個 PR,兩個人各做各的事。可以隨時切換視角對照著看。

你已經會的git clone、git add、git commit、git push
這次要新學的fork、git switch -c(分支)、git remote、網頁上的 Create pull request
1

Fork:在網頁上複製一份到你的帳號

你沒有權限改原作者的專案,所以先在 GitHub 上複製一份到「你自己的帳號」底下。這份叫 fork,你可以隨意修改。

  1. 用瀏覽器打開 github.com/{owner}/{repo}
  2. 點右上角的 Fork 按鈕。
  3. 確認 Owner 是你自己的帳號,按 Create fork。
你會看到網址變成 github.com/{me}/{repo},專案名稱下方多一行小字 forked from …。
注意fork 是網站上的按鈕,不是 git 指令,這一步不用打任何指令。
2

Clone「你的 fork」,不是原作者的

把你剛剛複製的那份抓到電腦上。如果 clone 的是原作者的 repo,之後 push 會因為沒有權限被拒絕。

git clone https://github.com/{me}/{repo}.git
cd {repo}
你會看到終端機顯示 Cloning into '…',電腦上多了一個專案資料夾,cd 之後你就在裡面了。
檢查網址裡的帳號必須是你自己({me}),不是原作者。
3

把原作者的 repo 登記成 upstream

原作者的專案會持續更新。你需要一條線能把他的最新內容拉下來。git 已經把你的 fork 取名 origin,我們再替原作者取名 upstream。只需要做一次。

git remote add upstream https://github.com/{owner}/{repo}.git
git remote -v
你會看到四行輸出:origin 兩行(指向你的 fork)、upstream 兩行(指向原作者)。
origin
你的 fork。你可以 push。
upstream
原作者的 repo。你只能從這裡拉(fetch),不能 push。
4

開一個新分支,不要直接在 main 上改

分支是平行的工作線。一個 PR 對應一個分支:你的 main 保持乾淨,也能同時做好幾個 PR 互不影響。分支名稱取成「看得出在做什麼」的短名字。

git switch -c {branch}
git branch
你會看到輸出 Switched to a new branch '{branch}';git branch 列表中目前分支前面有 *。
舊版 git如果 git switch 不能用(git 版本低於 2.23),改打 git checkout -b {branch}。
5

修改檔案、add、commit(你已經會了)

跟平常一樣。唯一的提醒:一個 PR 只做一件事,commit 訊息寫成「這次改了什麼」,審查的人會輕鬆很多。

git status
git add .
git commit -m "修正 README 的錯字"
你會看到git status 列出你改的檔案;commit 後顯示 1 file changed 之類的統計。
6

Push 到你的 fork

origin 就是你的 fork。-u 的作用是記住「這個本機分支對應 origin 上的哪個分支」,之後在這個分支只要打 git push 就好。

git push -u origin {branch}
你會看到最後幾行出現 * [new branch] {branch} -> {branch}。有時還會印出一個「Create a pull request」的網址,點它也能直接進入步驟 7。
檢查是 push 到 origin,不是 upstream(你對 upstream 沒有寫入權限)。
7

在 GitHub 網頁上開 Pull Request

到目前為止,修改只在你自己的 fork 裡。開 PR 才是真正「請對方看」的動作。

  1. 打開你的 fork 頁面 github.com/{me}/{repo}。
  2. 頂端會出現黃色橫幅,點綠色的 Compare & pull request。沒看到的話:Pull requests 分頁 → New pull request → compare across forks。
  3. 檢查兩端(下圖)。這是新手最容易填錯的地方。
  4. 填標題與說明(可用下方範本)。
  5. 按 Create pull request。還沒做完的話,改按旁邊下拉選單的 Create draft pull request,草稿 PR 不會被當成可以合併。
base · 目的地(對方)
repository{owner}/{repo}
branchmain
←
head · 來源(你)
repository{me}/{repo}
compare{branch}

讀法:「把我的 {branch} 合併進對方的 main」。

PR 說明範本(貼到說明欄)
## 這個 PR 做了什麼
修正 README 第 12 行的錯字 "recieve" → "receive"。

## 為什麼
使用者照文件操作時,容易因為拼字錯誤搜尋不到。

## 怎麼確認
在 GitHub 上預覽 README.md,確認文字顯示正確。

Closes #12

最後一行 Closes #12 是範例:對應到編號 12 的 issue,PR 合併時會自動把它關閉。沒有對應 issue 就刪掉這行。

你會看到跳到 github.com/{owner}/{repo}/pull/編號,狀態標籤是 Open。
8

等待審查;被要求修改時,「繼續 push」就好

PR 追蹤的是「分支」,不是某一次 commit。所以你在同一個分支再 push,PR 會自動更新,不需要重開 PR。

# 確認還在同一個分支,改完檔案後
git add .
git commit -m "依照 review 調整寫法"
git push
  1. 對方的意見會出現在 PR 的 Conversation 分頁,你會收到 email 通知。
  2. 想回覆就在該則留言下按 Reply;處理完可按 Resolve conversation。
  3. 改完後在右側 Reviewers 旁可按重新請求審查的圖示,或直接留言告訴對方「已更新」。
你會看到新的 commit 自動出現在 PR 的時間軸裡。
9

被合併之後:收尾與同步

對方按下 Merge 後,原作者的 main 已經有你的修改,但你的電腦和你的 fork 還是舊的。把它們同步,並清掉用完的分支。

git switch main
git fetch upstream
git merge upstream/main    # 把原作者最新的 main 合進你的 main
git push origin main       # 讓你的 fork 也更新
git branch -d {branch}     # 刪除本機分支
git push origin --delete {branch}    # 刪除 fork 上的分支(也可在 PR 頁面按 Delete branch)
你會看到git merge 顯示 Fast-forward 與你那次修改的檔案;之後想貢獻新東西,就從這個最新的 main 再開一個新分支。
懶人做法fork 的網頁上有 Sync fork 按鈕可以更新 fork 的 main,之後在本機打 git switch main 再 git pull 即可。
把以上步驟與你填的資料整理成清單,貼到筆記裡當檢查表。
你已經會的建立 repo、git push、git pull
這次要新學的網頁上的 Files changed、留言與 Review、三種 Merge 方式。幾乎不用打指令,全程在網頁上完成。
1

收到通知,找到那個 PR

有人開 PR 時,GitHub 會寄 email,右上角的通知鈴鐺也會亮起。

  1. 進入你的 repo 頁面 github.com/{owner}/{repo}。
  2. 點上方的 Pull requests 分頁(旁邊的數字就是待處理的 PR 數)。
  3. 點進該 PR 的標題。
ConversationCommits1Files changed1
你會看到PR 頁上方有三個分頁:Conversation(說明與討論)、Commits(提交清單)、Files changed(實際改了什麼)。狀態標籤是 Open。
2

先讀說明,再看自動檢查與衝突狀態

先理解「對方想解決什麼」,再看程式碼,判斷會快很多。

  1. 讀 PR 的標題與說明:這個修改的目的是你想要的方向嗎?
  2. 往下捲到 Checks(如果專案有設定自動測試):綠勾 = 通過,紅叉 = 失敗。
  3. 再往下看合併狀態:This branch has no conflicts with the base branch = 沒有衝突,可以合併。若顯示有衝突,請對方先處理(見「常見卡關」)。
3

在 Files changed 逐檔閱讀(最重要的一步)

這裡逐檔列出「改了什麼」:紅色 − 是被刪掉的,綠色 + 是新加的。

  1. 點 Files changed 分頁。
  2. 把滑鼠移到某一行左邊,會出現藍色 +,點下去就能針對「那一行」留言。
  3. 看完一個檔案,可以勾右上角的 Viewed 幫自己做記號。
11 ## Usage
12−Please recieve the file first.
12+Please receive the file first.
你在第 12 行留的範例留言謝謝你抓到這個錯字!第 31 行也有同樣的拼法,方便一起改嗎?
小技巧留言框工具列有個「Add a suggestion」圖示(±)。用它直接寫出你建議的新內容,發起者只要按 Commit suggestion 就能一鍵採用,不用來回溝通。
4

送出 Review:同意、要求修改,或只是留言

看完後,你需要正式告訴對方你的結論。

  1. 在 Files changed 頁右上角,按綠色的 Review changes。
  2. 寫一段總結(可以空白,但建議寫一兩句)。
  3. 三選一,然後按 Submit review。
選項
意思
什麼時候用
Comment
只是留言,不表態。
還有疑問、想先討論。
Approve
我同意,可以合併。
內容沒問題。
Request changes
要先修改才能合併。
有必須處理的問題,並寫清楚要改什麼。
對新手友善先說哪裡做得好,再提具體建議。「第 12 行改成 X」比「這樣不對」有用得多。
重要觀念Approve 不等於自動合併;Request changes 也不一定在每個 repo 都會強制擋住合併。實際能否 Merge,還要看權限、必要的審查人數、自動檢查(Checks)與分支保護規則。
5

(可選)把 PR 拉到自己電腦試跑

想親自跑跑看再決定?GitHub 替每個 PR 準備了一條特殊參照 pull/編號/head,可以直接抓成本機分支,不需要加對方的 remote。以下在你 clone 的 repo 資料夾裡執行。

git fetch origin pull/{n}/head:pr-{n}
git switch pr-{n}
# 測試完畢後回到 main 並刪掉暫時分支
git switch main
git branch -D pr-{n}
你會看到切換後,資料夾裡的檔案就是對方修改後的樣子。
安全提醒收到陌生人的 PR 時,不要未經檢查就在自己電腦上執行它的程式、安裝它新增的套件,或啟用它修改過的自動化流程(GitHub Actions)。先讀完 Files changed;有疑慮就留言詢問,或只在一次性的隔離環境裡試。
6

合併:選一種方式,按 Confirm

合併前的檢查:看過內容、Checks 是綠勾、沒有衝突。

  1. 捲到 PR 頁面最下方,綠色 Merge pull request 按鈕右邊有個下拉箭頭,可選合併方式。
  2. 選好後按該綠色按鈕,再按 Confirm merge。
方式
結果
適合
Create a merge commit
保留對方所有 commit,再多一個「合併」commit。
想完整保留歷史。
Squash and merge
把整個 PR 壓成 1 個 commit 放進 main。
新手專案首選:歷史乾淨,一個 PR 一個 commit。

把對方的 commit 逐一接在 main 後面,不產生合併 commit。

  • Checks 是紅叉:先弄清楚失敗原因,不要忽略。

看不到某個選項?可用的合併方式由 repo 設定決定(Settings → General → Pull Requests),可以自己勾選要開放哪些。
7

合併之後:清理並同步你的電腦

  1. PR 頁面若出現 Delete branch 就按下去,清掉用完的分支。如果 PR 是從別人的 fork 來的,通常沒有這顆按鈕,那條分支在對方的 fork 裡,由對方自己清理。
  2. 在你自己的電腦把 main 更新到最新:
git switch main
git pull
你會看到git pull 列出新增的 commit 與被修改的檔案。
別忘了在 PR 留一句謝謝。對第一次貢獻的人來說,這會有很大的鼓勵作用。
8

不打算合併時:友善地關閉

方向不符、重複、或暫時不需要,都可以不合併。

  1. 先在留言框寫清楚原因與感謝。
  2. 按 Close with comment(或 Close pull request)。
你會看到狀態標籤變成 Closed。關閉不會刪除任何東西;只要對方的分支還在,之後可以按 Reopen pull request 重新開啟。
同上,整理成檢查表。

同一個 PR,兩邊在同一個時間點各做什麼

點選下面的階段,看發起者與擁有者分別會看到什麼、該做什麼。

發起者

    擁有者

      初學者最常卡住的七個地方

      push 時出現 403 / Permission denied

      代表你正在 push 到沒有權限的地方,通常是 clone 時選到了原作者的 repo。先看 git remote -v:origin 必須是你自己的 fork。

      如果 origin 指到原作者,先完成步驟 1(fork),然後把名字換一換:

      git remote rename origin upstream
git remote add origin https://github.com/{me}/{repo}.git
git remote -v
git push -u origin {branch}
      我不小心直接在 main 上 commit 了

      不用慌,commit 還在。先用目前位置建立分支把它存起來,再把 main 拉回與原作者一致(這樣 main 就乾淨了)。

      git branch {branch}      # 在目前位置先存成一個分支,commit 都保留在這
git fetch upstream
git reset --hard upstream/main    # 把 main 拉回與原作者一致
git switch {branch}
      小心reset --hard 會丟掉「尚未 commit」的修改。執行前先打 git status,確認沒有未存的東西。
      PR 頁面顯示 “This branch has conflicts”(有衝突)

      意思是:在你開分支之後,原作者改了同一個地方,git 不知道該留誰的。發起者在本機處理:

      git fetch upstream
git switch {branch}
git merge upstream/main

      git 會停下來,並在衝突的檔案裡留下這種標記:

      <<<<<<< HEAD
你這邊的內容
=======
原作者那邊的內容
>>>>>>> upstream/main

      打開檔案,留下正確的內容,並把三種標記行整行刪掉。存檔後:

      git add .
git commit -m "解決與 main 的衝突"
git push

      擁有者不需要處理。留言請對方解決即可;簡單的衝突也可以按 PR 頁的 Resolve conflicts 在網頁上編輯,但建議由發起者處理,因為他最清楚自己想改什麼。

      合併後打 git branch -d,卻說 “not fully merged”

      如果擁有者用了 Squash and merge,你的所有 commit 被壓成一個「新」commit,git 在 main 上認不出你原本那幾個,所以不敢刪。

      只要你在網頁上確認 PR 已經是 Merged,就可以放心強制刪除:

      git branch -D {branch}
      我的 fork 落後原作者很多

      最簡單:到你 fork 的網頁,按 Sync fork → Update branch,然後在本機 git switch main、git pull。想用指令的話,就是步驟 9 前四行。

      建議:每次要開新分支前,先同步一次 main,再從最新的 main 開分支,可以減少很多衝突。

      我有寫入權限(自己的 repo / 團隊 repo),還需要 fork 嗎?

      不需要。直接 clone 原 repo,開分支,git push -u origin 分支名,然後在網頁上開 PR,base 是 main、compare 是你的分支。也就是跳過步驟 1 與 3,其他一樣。

      怎樣的 PR 比較容易被順利接受?

      給發起者

      • 小而專一:一個 PR 解一件事,比一次改十個地方好審十倍。
      • 先讀專案規則:看一下 CONTRIBUTING.md(貢獻指南)。
      • 大改動先討論:先開 issue 問對方有沒有興趣,免得白做。
      • 說明寫清楚:做了什麼、為什麼、怎麼確認。
      • 被要求修改不是被拒絕:這是正常的合作流程。

      給擁有者

      • 盡快回一句:就算還沒空審,先說「收到了」,對方會安心很多。
      • 意見要具體:指出行號與建議的寫法。
      • 分清必改與建議:必改用 Request changes,其他用 Comment。
      • 善用「允許維護者編輯」:若發起者勾選了 Allow edits by maintainers,小問題你可以直接幫他改。
      • 不合併也要說明原因,並感謝對方花時間。
