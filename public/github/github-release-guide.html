版本號是對使用者的承諾:用 tag 與 Release 發佈

把做好的成果正式交給使用者:決定版本號、貼上 tag、在 GitHub 上建立有說明與附件的 Release。重點是學會看改動內容決定該升哪一位。

TL;DR 版本號 MAJOR.MINOR.PATCH:壞掉舊用法升 MAJOR、新增功能升 MINOR、只修 bug 升 PATCH。流程是 git tag -a → git push origin 版本號 → 在網頁 Draft a new release。

版本號是對使用者的承諾

用「書的版次」來想

書出了新版,封面會寫第幾版,讀者才知道自己手上的是不是最新、改了什麼。軟體也一樣:tag 是在某個 commit 上貼的書籤(v1.2.0),Release 則是在這個書籤旁邊附上更新說明與可下載的檔案。

使用者看到版本號,就能判斷「升級會不會壞掉我的東西」。所以版本號要照規則升。

五個名詞

名詞
白話說明
tag
貼在某個 commit 上的固定標記,通常用版本號命名,例如 v1.2.0。
lightweight / annotated tag
輕量 tag 只是名字;annotated tag(-a)還附有作者、日期與說明,建議用這種。
SemVer(語意化版本)
MAJOR.MINOR.PATCH 的命名規則,見下圖。
Release
GitHub 上一頁正式的發佈,連結到一個 tag,可附說明與檔案。
Pre-release
標示為預覽版:還不穩定,不是給所有人用的。

全貌:三個數字,各代表一種承諾

版本號 v2.4.1 拆開來看。右邊是它在 GitHub 上的樣子:tag 加上 Release。

  1. 2MAJOR:有不相容的改動。使用者升級前必須看說明。
  2. 4MINOR:新增功能,舊功能照舊。
  3. 1PATCH:只修 bug,行為不變。

照著做:七個步驟

1

先決定這次是哪一種升級

版本號不是亂取的。問自己:這次改動,會不會讓舊的用法壞掉?

這次改了…
升哪一位
例子
修 bug、文字更正,行為不變
PATCH
1.2.3 → 1.2.4
新增功能,舊功能照常可用
MINOR(PATCH 歸零)
1.2.4 → 1.3.0
改了既有用法、移除功能
MAJOR(其餘歸零)
1.3.0 → 2.0.0
還在開發、尚未穩定
0.x.y,或加上 -beta.1 這類後綴
0.9.0、1.0.0-rc.1
小技巧第一次正式發佈通常從 v1.0.0 開始;還不穩定就先用 v0.1.0。
2

確認要發佈的內容已經在 main 上

tag 會貼在目前所在的那個 commit。貼錯位置,版本號就對不上內容。

git switch main
git pull
git status
git log --oneline -n 3
你會看到git status 顯示 nothing to commit, working tree clean 與 up to date with 'origin/main'。
注意沒有 clean 或沒有 pull 到最新,就先處理,不然 tag 會貼在不是你想發佈的 commit 上。
3

建立 annotated tag

-a 表示 annotated,-m 是這個版本的簡短說明。

git tag -a {ver} -m "Release {ver}"
git tag
git show {ver} --stat
你會看到git tag 列出所有 tag,其中有 {ver};git show 顯示 tag 的資訊與它指向的 commit。
小技巧貼錯了想刪掉(還沒 push):git tag -d {ver}。
4

把 tag 推上 GitHub

tag 不會隨著 git push 一起上去,要另外送。

git push origin {ver}
# 一次推送全部本機 tag:
# git push origin --tags
你會看到終端機顯示 * [new tag] {ver} -> {ver}。在 GitHub 的 repo 頁面,切換分支選單旁的 Tags 可以看到它。
5

在網頁上建立 Release

tag 只是標記。Release 才是給使用者看的發佈頁。

  1. 在 repo 首頁,右側 Releases 區塊點 Releases(或用網址 github.com/{me}/{repo}/releases)。
  2. 按 Draft a new release(若是第一次,也可能顯示 Create a new release)。
  3. Choose a tag 下拉選擇剛推上去的 {ver}。
  4. Release title 填 {ver} 或帶一點說明的標題。
你會看到頁面進入編輯狀態,左上顯示你選的 tag,下方是一個說明編輯框。
6

寫 Release notes(可用自動產生)

說明要寫給使用者看:新增什麼、修了什麼、需要注意什麼。

  1. 在 Describe this release 裡,按 Generate release notes,GitHub 會依合併過的 PR 自動列出清單與貢獻者。
  2. Previous tag 選上一個版本,清單才會是「這次與上次之間」的差異。
  3. 自動產生的內容可以再編輯。有不相容的改動,務必在最前面寫出來。
Release notes 範例
## 新增
- 搜尋支援依標籤篩選 (#34)

## 修正
- 修正匯出 CSV 時中文亂碼 (#36)

## 注意
- 設定檔欄位 `theme` 更名為 `colorTheme`,請參考遷移說明
你會看到說明框出現依 PR 整理的條列;預覽分頁可看到最後的樣子。
7

選發佈類型、附檔案、發佈

Release 有三種常見狀態,依成熟度選。

  1. 有要附上的安裝檔或壓縮檔,拖曳到 Attach binaries 的區域。
  2. 還不穩定:勾 Set as a pre-release,標成預覽版。
  3. 正式版:勾 Set as the latest release(不勾的話,GitHub 依版本號決定哪個是最新)。
  4. 還沒寫完:按 Save draft 存成草稿,只有管理者看得到。
  5. 準備好了,按 Publish release。
你會看到Release 頁面公開,綠色標籤 Latest 或橘色標籤 Pre-release。repo 首頁右側 Releases 區塊顯示最新版本號。
提醒GitHub 會自動附上「原始碼的壓縮檔」(Source code .zip / .tar.gz),不需要自己上傳。若要附編譯好的檔案,才需要在步驟中附檔。

發佈的三種狀態

點選下面的狀態,左邊看你怎麼做,右邊看對使用者有什麼意義。

你怎麼做:

    對使用者意味著:

      常見卡關

      Release 的 Choose a tag 下拉選單找不到我的 tag

      多半是 tag 還沒推到 GitHub。用 git push origin 版本號 推上去,重新整理頁面。也可以直接在下拉裡輸入新的版本號並選 Create new tag,這時要再選 Target 是哪個分支。

      tag 貼錯 commit 了

      如果還沒推上去,git tag -d 版本號 刪掉重打。已經推上去,但還沒對外宣布,先在 GitHub 刪掉那個 Release 與 tag,再重打。已經被人用了,就別動它,發一個新的 PATCH。

      git tag -d {ver}
git push origin --delete {ver}
      發佈後發現有 bug

      不要改已發佈的版本。修好之後發一個新的 PATCH 版(例如 v1.2.4),說明裡簡短交代修了什麼。

      我應該用 v1.0.0 還是 1.0.0?

      兩者都可以。多數專案加前綴 v。重點是全專案保持一致,工具與腳本才不會出錯。

      可以讓 GitHub 自動發 Release 嗎?

      可以,用 GitHub Actions 在推上 tag 時自動建立 Release 並附上建置好的檔案,見第 11 篇。
