小而專一的 PR 加具體友善的意見,review 才有效

這是第 6 篇 Pull Request 的延伸。同一個 PR 分兩個視角講:「被審查的人(作者)」和「審查別人的人(審查者)」,最後再說團隊怎麼用規則集、CODEOWNERS 與 PR 範本把流程固定下來。

TL;DR 作者:PR 要小、先自審、說明寫清楚、每則意見都回應。審查者:先讀說明與 Checks、按順序看 diff、意見分必改與建議。團隊:用 Ruleset 與 CODEOWNERS,讓審查變成規則而不是自覺。

Code Review:讓第二雙眼睛看過再合併

用「出書前的校對」來想

作者再仔細也會有盲點。Code Review 就是請另一個人在合併前看一遍:找 bug、問疑問、提改善,也讓專案知識不被單一個人壟斷。它的目的不是挑錯,而是讓合併進 main 的東西更可靠。

好的 review 靠兩件事:小而專一的 PR,與具體而友善的意見。團隊規範(規則集、Code Owner、PR 範本)則讓這件事不靠自覺也能執行。

七個名詞

名詞
白話說明
Review
對一個 PR 送出的整體評語,結論有 Comment / Approve / Request changes 三種。
Suggestion
留言時直接寫出建議的新內容,作者按一下就能採用。
Resolve conversation
某則討論處理完畢後標記為已解決。
Required approvals
規則要求的最少核准人數。沒達到,Merge 按鈕不會放行。
Code Owner
某些檔案的指定負責人。這些檔案被改動時,會自動請他審查。
Ruleset / Branch protection
保護重要分支的規則,例如必須經過 PR、必須通過檢查、禁止強制推送。
PR template
開 PR 時自動預填的說明範本。

全貌:審查是一個來回的迴圈

先看地圖。作者與審查者在中間來回,直到規則放行。

  1. 1審查 ↔ 修改:審查者留意見,作者改完 push,PR 自動更新。作者審查者
  2. 2規則放行:核准數、Checks、Code Owner 都滿足,才能 Merge。審查者

選一個視角,照著步驟做

同一個 PR,兩個人各做各的事。可以隨時切換視角對照著看。

你已經會的開 PR(第 6 篇)、在同一分支再 push
這次要新學的怎麼讓 PR 好審、怎麼回應意見、重新請求審查
1

把 PR 縮小

審查品質和 PR 大小成反比。一個 PR 只做一件事,審查者才有力氣看仔細。

  1. 一個 PR 解一個問題。順便重構、順便改格式,請另開 PR。
  2. 改動超過幾百行,考慮拆成幾個依序合併的小 PR。
  3. 拆不開時,在說明裡寫「建議閱讀順序」。
小技巧好用的自問:「審查者能在 15 分鐘內讀完並理解嗎?」
2

送審之前先自己審一遍

多數低級問題,作者自己看 Files changed 就能發現。這能大幅減少來回次數。

  1. 開 PR 後先點 Files changed,像審查者一樣從頭看。
  2. 找:誤加的檔案、遺留的除錯輸出、註解掉的程式碼、密碼或 token。
  3. 在你覺得不直覺的地方,自己先留一則註解說明為什麼。
重要發現密碼或 token 被 commit 進去,請看第 10 篇,不要只是刪掉再 push。
3

寫一份讓審查者好上手的說明

說明是審查者的導讀。沒寫清楚,他只能自己猜你的意圖。

PR 說明範本(團隊可存成 PR template)
## 這個 PR 做了什麼
(一兩句話)

## 為什麼
(背景或對應的 Issue,例如 Closes #12)

## 怎麼確認
(測試方式、截圖)

## 想請你特別看
(例如:第 40 行的邊界條件是否合理)
  1. 還沒做完就先開 Draft pull request,草稿不會被當成可以合併。
  2. 準備好了,在 PR 頁面按 Ready for review。
你會看到PR 頁面狀態從灰色的 Draft 變成 Open,審查者會收到通知。
4

收到意見:回覆、修改、標記解決

每一則意見都需要一個回應。同意就改,不同意就禮貌地說明理由。

  1. 對方用了 suggestion:在該則留言按 Commit suggestion 一鍵採用。
  2. 需要自己改:在同一個分支修改、commit、git push,PR 會自動更新。
  3. 處理完那則討論,按 Resolve conversation;不同意就留言說明,讓對方決定是否解決。
git add .
git commit -m "依 review 調整命名"
git push
你會看到新 commit 出現在 PR 時間軸,被處理的討論折疊成「Resolved」。
5

重新請求審查

你改完了,但審查者不知道。主動通知他。

  1. 在 PR 右側 Reviewers 旁,點對方名字旁的重新整理圖示(Re-request review)。
  2. 或留言一句「已更新,麻煩再看一下」,並點名 @對方。
你會看到審查者再次收到通知,審查狀態回到等待中。
6

合併前最後確認

按 Merge 之前,把清單走一遍。

  1. 所有討論都已 Resolve,Checks 是綠勾。
  2. 沒有衝突;有的話先回到第 3 篇的方式在本機解決。
  3. 符合規則要求的核准數(有 Code Owner 時,包含他的核准)。
  4. 合併後,若 PR 頁有 Delete branch 就按下去清掉。
你會看到Merge 按鈕可點(綠色)。被規則擋住時,按鈕灰掉,並列出還缺什麼。
你已經會的閱讀 Files changed、送出 Review(第 6 篇)
這次要新學的讀 diff 的順序、留言分輕重、什麼時候不該 Approve
1

先讀說明和 Checks,再看程式碼

知道作者想解決什麼,才能判斷做法對不對。Checks 紅叉時,先請作者處理,不必急著逐行看。

  1. 讀標題、說明與連結的 Issue。
  2. 往下看 Checks:綠勾通過、紅叉失敗。
  3. 想不通目的時,先留言問,而不是自己猜。
2

按好的順序讀 diff

從大到小:先看「做了什麼」,再看「怎麼做」。

  1. 先看測試檔案:它們說明了作者想保證的行為。
  2. 再看對外的介面、設定、資料結構,最後才是實作細節。
  3. 看完一個檔案,在 Files changed 右上角勾 Viewed 做記號。
小技巧心裡問這幾件事:對嗎?看得懂嗎?會不會壞掉別的地方?有測試嗎?有沒有敏感資訊?
3

留言要具體,而且分輕重

讓作者一眼看出「哪些非改不可」。把行號、原因和建議寫在同一則留言裡。

類型
怎麼寫
範例
必改
說明問題與原因
這裡沒處理 null,使用者沒填時會當掉。
建議
加上 nit: 前綴,表示可改可不改
nit: d 可以改叫 days,比較好讀。
疑問
用問句,不要預設對方錯
這個延遲設 500ms 是有什麼考量嗎?
稱讚
具體說好在哪
這個拆法很清楚,測試也好讀。
  1. 在行號旁的 + 留言;簡單修改用 Add a suggestion(±)直接寫出新內容。
  2. 多則意見先用 Start a review / Add review comment 累積,最後一次送出,避免作者被一則一則通知轟炸。
4

送出你的結論

看完後,正式告訴作者你的結論。

  1. Files changed 頁右上角按 Review changes,寫一段總結。
  2. 三選一:Comment(只是留言)、Approve(我同意)、Request changes(有必改的問題),按 Submit review。
注意只有真的有「必改」的問題才用 Request changes。只是偏好或 nit,用 Comment 或直接 Approve 並附註。
5

作者更新後,再看一次

不必重讀全部,看「上次之後改了什麼」就好。

  1. 收到更新通知後,點 PR 的 Commits 或 Files changed,只看新的 commit。
  2. 意見處理好了,幫忙或請作者按 Resolve conversation,並改成 Approve。
你會看到審查狀態從 Changes requested 變成綠色的 Approved。
6

什麼時候不該按 Approve

Approve 代表你對這次改動負一份責任。

  1. 你沒有真的看過。只按 LGTM(Looks Good To Me)而沒看,比不審查更糟,因為會給人錯誤的安心。
  2. 還有疑問沒獲得回答。
  3. 超出你能判斷的範圍時,說出來並請更適合的人看。
你會看到對方會明白你看了哪些部分、哪些沒把握,而不是被一個空洞的 Approve 帶過去。

團隊規範:讓 review 不靠自覺也能執行

下面四步通常由 repo 的管理者設定。規則功能的可用範圍依方案與 repo 類型而定(私人 repo 可能需要付費方案),實際畫面以 GitHub 為準。

1

放一份 PR 範本

每個 PR 一開始就有說明的骨架,作者不用每次自己想要寫什麼。

  1. 在 repo 建立檔案 .github/pull_request_template.md,內容用步驟 3 的範本。
  2. commit 並 push 到預設分支。
你會看到之後有人開 PR,說明欄自動出現你的範本。
2

設定 CODEOWNERS

指定「這些檔案由誰負責」。有人改到時,GitHub 會自動請他審查。

CODEOWNERS(可放在 .github/、根目錄或 docs/)
# 每一行:檔案樣式 + 負責人(@帳號 或 @組織/團隊)
# 最後一個符合的規則優先
*           @your-name
/docs/      @doc-team
*.js        @frontend-team
  1. 把檔案放在 .github/CODEOWNERS、repo 根目錄或 docs/CODEOWNERS 其中之一(GitHub 依這個順序找第一個)。
  2. 每行是「檔案樣式 + 一個或多個負責人」,最後一個符合的規則優先。
你會看到PR 的 Reviewers 欄自動出現對應的負責人。
3

建立 Ruleset 保護 main

把「必須經過審查才能合併」寫成規則,而不是靠大家自覺。Ruleset 是較新的做法,同一個分支可以同時套用多組規則;舊的 Branch protection rule 仍可使用,但官方文件把 ruleset 當作替代方案。

  1. 在 repo 頁面進 Settings,左側找到 Rules → Rulesets。
  2. 按 New ruleset → New branch ruleset,取個名字,例如 protect-main。
  3. Enforcement status 選 Active(啟用)。
  4. 目標分支選預設分支(Include default branch)。
  5. 勾選要的規則,常見四項:要求經過 PR 才能合併、設定必要的核准人數、要求 Code Owner 核准、要求狀態檢查(Checks)通過;另外建議勾禁止強制推送。
  6. 按 Create。
你會看到規則集出現在 Rulesets 清單,狀態是 Active。
注意規則的確切名稱與選項順序會隨 GitHub 更新而調整,請以畫面上的字為準;設定前建議先在練習用的 repo 試一次。
4

驗證:開一個測試 PR

規則有沒有生效,實際試一次最準。

  1. 開一個測試 PR,在還沒有核准時看 Merge 按鈕。
  2. 規則生效時,按鈕被擋住,並列出還缺什麼(核准、Checks、Code Owner)。
  3. 也試試直接 git push origin main,應該被拒絕。
你會看到按鈕灰色,畫面寫著需要至少一位核准;直接 push 到 main 顯示被規則拒絕。

同一個 PR,兩邊在同一個時間點各做什麼

作者

    審查者

      常見卡關

      Merge 按鈕是灰的,不知道缺什麼

      往下捲到 PR 頁最底的合併區塊,GitHub 會列出每個還沒滿足的條件:需要幾個核准、哪個 Check 沒過、哪位 Code Owner 還沒審、還有未解決的討論。逐項處理即可。

      審查者很久沒回

      先確認是否真的被請求了(Reviewers 欄有沒有他)。隔一兩天留言禮貌提醒,或請團隊裡另一位審查者;不要自己繞過規則。

      意見互相衝突,不知道聽誰的

      把兩種意見和你的取捨寫在留言裡,點名雙方,請他們在 PR 上直接討論。團隊有決策慣例就照做。

      審查者說我的 PR 太大了

      這是最常見也最合理的意見。把 PR 拆成幾個依序合併的小 PR,每個只做一件事。拆開之後,review 的速度與品質都會上升。

      我是 repo 擁有者,可以略過規則嗎

      管理者通常能繞過規則(可在規則集裡設定誰能 bypass),但最好養成「自己也走流程」的習慣。很多團隊會把管理者也納入規則。
