密碼一旦 push,就當作外洩

用「家裡鑰匙」來想

你把鑰匙放在公開的地方,就算幾分鐘後拿回來,也無法確定有沒有被人複製。所以正確做法不是「把鑰匙藏好」,而是把鎖換掉。Secret(密碼、API 金鑰、token、私鑰)也一樣:push 過,就必須先在服務端讓它失效。

本篇分三層:預防(不讓它進 repo)、偵測(Secret scanning、push protection)、善後(撤銷、清理)。再加上 Dependabot,處理相依套件的漏洞。

六個名詞

名詞
白話說明
secret
不能公開的憑證:密碼、API key、token、私鑰、資料庫連線字串。
Secret scanning
GitHub 掃描 repo 內容,發現看起來像憑證的字串就提出警示。

全貌:先讓舊金鑰失效,再談清理

順序很重要。很多人先忙著清歷史,卻忘了金鑰早就被抄走。

  1. 1撤銷 / 更換:到服務商後台讓舊金鑰失效,換新的。
  2. 2清理歷史:改寫歷史把它移除。這只是補強,不能取代第 1 步。
  3. 3開啟預防:.gitignore、push protection、Secret scanning、Dependabot。

照著做:七個步驟

1

預防:不要讓 secret 進入 repo

最好的處理是它從來沒有進過 repo。

  1. 把 secret 放在 .env,並寫進 .gitignore(見第 2 篇)。
  2. 程式從環境變數讀取,不要把字串寫死在程式碼裡。
  3. 另外提交一份只有欄位名稱的 .env.example,讓別人知道要設定什麼。
預防範例
# .gitignore
.env
!.env.example

# 程式裡改成讀環境變數(Node.js 範例)
const key = process.env.API_KEY;
你會看到git status 看不到 .env,表示它被忽略了。
2

發現已經 commit(甚至 push)了:先別慌,照順序

不要先刪檔案、不要先 revert,那都無法讓已外洩的金鑰失效。

  1. 立刻到該服務的後台撤銷 / 更換這把金鑰(例如雲端服務的 API keys 頁、資料庫的密碼設定、GitHub 的 Personal access tokens 頁)。
  2. 確認新金鑰已設定好,舊金鑰真的失效了。
  3. 檢查服務的使用紀錄,看有沒有不明的使用。有的話,視情況通知相關人員。
重要git revert 與刪除檔案只會新增一個 commit,舊的 commit 仍然留著密碼。只有撤銷才有用。
3

(選做)清理歷史

撤銷之後,舊金鑰已經沒用,清理歷史只是讓它不要繼續被看到。官方文件建議用 git filter-repo(較新的版本才有 --sensitive-data-removal 這個選項,請查閱工具說明)。

  1. 先把 repo 重新 clone 一份乾淨的副本來操作,避免弄壞原本的工作資料夾。
  2. 依你的情況選一種做法:整個檔案從歷史移除,或用文字檔列出要替換的字串。
  3. 檢查結果沒問題,再強制推送到 GitHub。
# 安裝:pip install git-filter-repo
# 範例:把 .env 從所有歷史移除
git filter-repo --invert-paths --path .env

# 範例:把檔案裡列出的字串替換掉(replacements.txt 每行一條規則)
# git filter-repo --replace-text replacements.txt

# 清理完,強制推送(會改寫整個雲端歷史)
# git push --force --mirror origin
風險這會改寫所有 commit 代號、移除簽章,進行中的 PR 可能受影響。其他人手上的 clone 與 fork 仍然保有舊資料,你要通知他們重新 clone,並且不要用舊 clone 再 push 回來。GitHub 上的快取檢視與 PR 參照,需要另外聯絡 GitHub Support 才會清除。強制推送前務必先和團隊確認。
4

開啟 Secret scanning 與 push protection

讓 GitHub 在 push 的當下就幫你擋。

  1. 個人帳號的 push protection,在 GitHub.com 上預設就是開啟的,會擋住你把 secret 推到公開 repo。
  2. repo 層級的 push protection 預設是關閉的,要由 repo 管理者(或組織擁有者)開啟。入口在 repo 的 Settings → 側邊欄 Security and quality 區塊的 Advanced Security。
  3. 不同 repo 類型與方案可用的功能不同(例如部分功能屬於 GitHub Secret Protection),請依你頁面上實際出現的選項為準。
你會看到push 含有 secret 的 commit 時,終端機顯示 push 被拒絕,並說明是哪個檔案、哪一行。
小技巧被擋時的正確做法:移除 secret、改用環境變數、重新 commit。不要選「略過」,除非你確認那是誤報或測試用資料。略過會留下紀錄並通知管理者。
5

開啟 Dependabot alerts

你的程式用了別人的套件。套件有漏洞,你的程式也受影響。Dependabot 幫你看。

  1. 進入 repo 的 Settings。
  2. 側邊欄 Security and quality 區塊 → Advanced Security。
  3. 在 Dependabot alerts 右邊按 Enable。
你會看到repo 的 Security 分頁出現 Dependabot 的警示清單(沒有漏洞時是空的)。
注意設定頁的區塊名稱與位置會調整,若看不到,請用設定頁上方的搜尋,或以官方文件為準。
6

讓 Dependabot 自動開 PR 升級套件

有警示後,可以讓它直接開 PR 把套件升級到修好的版本;也可以設定定期檢查更新。

.github/dependabot.yml(版本更新)
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"   # 依你用的套件管理員:npm、pip、maven …
    directory: "/"              # 設定檔(如 package.json)所在的位置
    schedule:
      interval: "weekly"        # 每週檢查一次
  1. 把上面內容存成 .github/dependabot.yml,依你的專案改 package-ecosystem。
  2. commit 並 push 到預設分支。
  3. 之後 Dependabot 依排程開 PR,你像審查一般 PR 一樣看過、確認測試通過再合併(見第 7 篇)。
你會看到repo 的 Pull requests 出現由 dependabot[bot] 開的 PR,說明裡寫了升級的版本與變更內容。
7

在 GitHub Actions 裡用 secrets,不要寫死

CI 需要部署金鑰時,放在 Actions secrets,不要寫進 workflow 檔。

  1. repo 的 Settings → 側邊欄 Secrets and variables → Actions。
  2. 在 Secrets 分頁按 New repository secret,填名稱與值,按 Add secret。
  3. workflow 裡用 ${{ secrets.名稱 }} 取用(詳見第 11 篇)。
workflow 片段
steps:
  - name: Deploy
    env:
      API_KEY: ${{ secrets.API_KEY }}   # 值不會出現在日誌
    run: ./deploy.sh
你會看到secret 儲存後只能覆蓋或刪除,看不到原本的值;日誌裡出現的值會被遮成 ***。

常見卡關

我 commit 了密碼,但還沒 push

好消息:還沒離開你的電腦。用第 8 篇的方式把那個 commit 拆掉(git reset --soft HEAD~1),把 secret 移出去再重新 commit。仍建議更換金鑰,以防萬一曾經被別的工具(如雲端同步)看到。

我的 repo 是私人的,還需要撤銷嗎?

需要。私人 repo 仍然有協作者、CI 與整合服務能看到,而且 repo 之後可能被改成公開或被 fork。金鑰外洩的處理標準不因 repo 公開與否而不同。

push 被 push protection 擋住,但我確定是誤報

終端機訊息會提供略過的連結與選項(例如「是測試用資料」「是誤報」)。選擇後可以再 push,但這會留下紀錄並通知管理者。能改成不像金鑰的測試資料就改。

Dependabot 開了太多 PR

在 dependabot.yml 把 interval 改成 monthly,或設定 open-pull-requests-limit 限制同時開啟的數量,並把相關更新設定成分組。

我不知道自己有沒有把 secret commit 過

可以搜尋歷史:git log -S"可疑字串" --oneline 會列出新增或移除過這個字串的 commit。也可以到 repo 的 Security 分頁看 Secret scanning 有沒有警示。
